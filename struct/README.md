# pg_repack 1.5.3, struct-throttle build (STR-7151)

A client-only fork of pg_repack 1.5.3 that repacks a bloated table gently:

- it copies in **paced slices** instead of one full-speed `INSERT … SELECT`;
- it **backs off automatically** while the database is under pressure;
- it **paces the log replay**;
- a **maximum-runtime guard** ends the run after a set time;
- it prints a **progress line** every minute;
- it **cleans up by itself** when the job is stopped.

The swap, the trigger and log design, and pg_repack's consistency model are
unchanged. The server keeps running the **stock** 1.5.3 extension.

Background: the 11/4 run on `t1t76sk7w9.agent_execution_steps` copied at full
speed. Disk bandwidth hit 90–95% and app requests stalled. Storage reached
94.48%, and the run had to be stopped by hand with `abort-repack.sql`, because
stopping the container does not stop a running `INSERT … SELECT`.

Port these into `packages/deployment-configs/pg-repack/`: `patches/`,
`Dockerfile`, `repack.sh`, and this README as the runbook.

## Knobs

Every knob is a CLI flag with an env var in `repack.sh`. An unset or empty env
var means "use the default". Durations accept `ms`, `s`, `m`, `h` and `d`;
a bare number means seconds.

| Env var | Flag | Default | Off | What it does |
| --- | --- | --- | --- | --- |
| `REPACK_COPY_SLICE_PAGES` | `--copy-slice-pages` | 1024 | 0 = one statement | Heap pages per copy slice. On `t1t76sk7w9`, 1024 pages ≈ 270 MB of live data (11 rows/page, ~23 kB of TOAST per row). |
| `REPACK_DUTY_CYCLE` | `--duty-cycle` | 0.33 | 1 | After a slice that took *t*, sleep *t × (1/X − 1)*. |
| `REPACK_MAX_SLICE_SLEEP` | `--max-slice-sleep` | 30s | 0 = no cap | Upper bound on one pacing sleep. |
| `REPACK_BACKOFF_IO_WAITERS` | `--backoff-io-waiters` | 16 | 0 | Pause while ≥ N *other* client backends are active with `wait_event_type = 'IO'`. |
| `REPACK_BACKOFF_WAL_GB` | `--backoff-wal-gb` | 35 | 0 | Pause while `sum(size) FROM pg_ls_waldir()` ≥ G GB. |
| `REPACK_BACKOFF_REPLICA_LAG` | `--backoff-replica-lag` | 60s | 0 | Pause while `max(replay_lag)` in `pg_stat_replication` ≥ S. |
| `REPACK_BACKOFF_STEP` | `--backoff-step` | 10s | — | Re-check interval while paused. |
| `REPACK_BACKOFF_MAX` | `--backoff-max` | 600s | 0 | If one pause lasts longer, log a WARNING every step. The run keeps waiting; it never aborts for this. |
| `REPACK_MAX_RUNTIME` | `--max-runtime` | 4h | 0 | Abort and clean up after this long. This bounds how long the copy snapshot holds back vacuum database-wide. |
| `REPACK_PROGRESS_INTERVAL` | `--progress-interval` | 60s | 0 | Seconds between progress lines. |
| `REPACK_APPLY_COUNT` | `--apply-count` | 1000 | — | Log rows per replay batch (a stock flag). |

Back-off is checked before every copy slice and every replay batch. Pacing
applies after each slice and after each replay batch, **except** the final
`apply_log` under the exclusive lock right before the swap, which must stay
short. Index builds are neither paced nor backed off, because each
`CREATE INDEX` is a single statement.

The throttle only works in `--no-order` mode, which `repack.sh` always uses.
Passing a copy or back-off flag together with ordering (`-o`, or the default
CLUSTER order) is an error. In ordered mode the client behaves like stock
1.5.3 and prints nothing new, except that `--max-runtime` and SIGTERM handling
still apply.

**Azure privileges, checked on prod 11/5:** `postgres` is not a superuser, but
it inherits `pg_monitor` and `pg_read_all_stats` through `azure_pg_admin`. So
`pg_ls_waldir()` is callable, and `replay_lag` and other roles' wait events
are visible. If a run uses a role without these, the client logs one WARNING
per affected signal and carries on (the WAL signal is disabled).

## What a run prints

At the start, **for information only, not a gate**, the client prints the
table's size on disk, an estimate of its live data (it samples about 2000
heap pages and sums `pg_column_size` per column, which reads TOAST pointers
without fetching the values), and the projected peak extra space (live +
current index size + about 20 GB of WAL).

**`REPACK_DRY_RUN=1` prints the same lines without changing anything**, so it
is a quick way to size a run.

```
INFO: size (informational, not a gate): table=… on_disk=… (heap …, toast …, indexes …)
INFO: size: live_estimate=… (sampled ~2000 of … heap pages); projected_peak_extra=… (live + indexes … + ~20GB WAL)
INFO: progress: table=… phase=copy pages=120832/356965 (33.8%) eta=1h12m written=31.80GB rate=16.2MB/s phase_elapsed=34m10s backoff=none wal=24.10GB io_waiters=2 replica_lag=0.8s snapshot_age=34m12s xmin_age=1834567
INFO: back-off: phase=copy signal=wal-gb value=35.2; pausing
INFO: back-off cleared after 1m40s; resuming copy
```

In a progress line:

- `phase` is one of copy, index, apply or swap.
- `written` is the current size of `repack.table_<oid>`, including its TOAST and indexes.
- `rate` is the write rate since the previous line. During pacing sleeps it is low by design.
- `snapshot_age` / `xmin_age` show how long the copy snapshot has been holding back vacuum.

## Stopping a run (D4)

Stop the job execution. Container Apps sends SIGTERM. `repack.sh` forwards it
to `pg_repack`, which then:

1. cancels its running statement (`PQcancel`);
2. rolls back the copy transaction, which removes the new table's files;
3. reconnects, takes the table lock briefly, and calls `repack.repack_drop()`
   to remove the trigger, log table and types;
4. exits non-zero with one line:

```
pg_repack aborted cleanly: reason=SIGTERM table=t….agent_execution_steps phase=copy copied_pages=1024/356965
```

`reason` is `SIGTERM`, `SIGINT` or `max-runtime`. If the signal arrives after
the swap committed, the line says `pg_repack interrupted after swap`. In that
case the table *was* repacked and only the temporary objects were dropped.

If cleanup itself fails, for example because it could not get the table lock
within `--wait-timeout`, the last line is
`pg_repack abort cleanup FAILED … run abort-repack.sql`.

**SIGKILL still leaves leftovers.** SIGKILL is what happens if the grace
period runs out, or the node dies. Run `abort-repack.sql` through
`run-prod-sql.py`; it terminates `pg_repack` sessions and drops the extension
with CASCADE. Slicing helps even here: the server backend stops at the end of
the current slice when its client is gone, instead of copying the whole table
the way the stock client's single statement did on 11/4.

**Grace period:** `terminationGracePeriodSeconds` is not part of the Container
Apps *job* template in any API version we checked (2024-03-01 to 2025-07-01).
It exists only for container apps. The job therefore gets the platform
default. In local tests, clean-up took well under a second after SIGTERM.
On prod it is dominated by the brief exclusive lock that `repack_drop` needs,
and `--no-kill-backend` waits up to `--wait-timeout` (120 s) for it. If a
stop is ever SIGKILLed before the "aborted cleanly" line appears, use
`abort-repack.sql`.

## Planning a prod run (lessons from 11/4)

- **The limit is Azure's 95% read-only line, not the autogrow trigger.** On
  `homestead-prod-wus3` that is about **108 GB free**; `storage_percent` uses a
  denominator of about 2,171 GB. Azure does not autogrow during heavy WAL use.
- **Go rule:** free space before the run, minus (live data + ~6 GB of
  indexes), minus ~20 GB of WAL, must stay **≥ 130 GB**.
- **Size from live data**, measured over the MCP as `sum(pg_column_size(payload))`
  by date range (one whole-table sum times out), or from the dry-run estimate.
- **Monitor (D3; the tool does not watch storage):** `storage_free`,
  `storage_percent`, `txlogs_storage_used`, `disk_bandwidth_consumed_percentage`,
  `disk_queue_depth` and app error rates, every 1–2 minutes.
- **Tune:** aim for disk bandwidth ≤ ~50% during the copy. Lower
  `REPACK_DUTY_CYCLE` to go gentler; change `REPACK_COPY_SLICE_PAGES` only if
  slices take much longer than a few seconds.
- **To abort:** stop the job execution and wait for the "aborted cleanly"
  line. Fall back to `abort-repack.sql`, which a person runs.
- **The cost of the single snapshot (D1):** while the copy runs, vacuum cannot
  remove rows deleted anywhere in the database, including the archiver's
  deletes. `--max-runtime` bounds this. Watch `snapshot_age` in the progress
  lines.

Agents may build the image, update the job's image and env vars, and read its
logs. **A person starts every execution.**

## Testing locally

`test/` needs PostgreSQL 16 with the stock pg_repack 1.5.3 extension, built
from the same tag.

```sh
export PGHOST=localhost PGPORT=55432 PGUSER=postgres PGDATABASE=postgres
psql -v rows=20000 -f test/setup.sql   # ~1.3 GB, TOAST-heavy, half the rows deleted
test/matrix.sh                         # correctness for every mode + every abort path
```

Every case runs with a concurrent pgbench writer: inserts, archiver-style
deletes and updates. Each writer statement also updates a shadow table of
`id → md5(payload)` in the same statement. `verify.sql` then checks:

- the repacked table matches the shadow exactly (row count and per-id hash);
- all indexes and constraints, including the FK, are present and valid;
- nothing is left in the `repack` schema and no `repack_trigger` remains.
